# 前端开发习惯工程化指南

> 让 Agent 稳定遵循你的规则与习惯的四层框架
> 2026-07-28

---

## 一、问题背景

许多前端开发者在日常工作中已经形成了自己成熟的习惯：特定的目录结构、命名规范、接口封装方式、状态管理策略等。然而，在与 AI Agent 协作时，这些习惯往往无法被有效传递，导致：

- Agent 生成的代码风格不一致，需要反复修正
- 创建新工程时目录结构不完整，缺少关键文件
- 类型定义随意、出现 `any` 等不符合团队规范的写法
- 每次对话都需要重新叮嘱同一套规则

> **核心转变：** 从「口述叮嘱」→「文件化规则」→「工具化校验」。规则文件让 Agent 知道怎么做，工程载体让它不得不这么做。

## 三、第一层：提取习惯

不要一上来就写规范文件。先从你已经做过的项目里复盘，找出你**真正每次都重复做的事情**。

### 提取清单

对着你最近 2-3 个项目，逐一回答以下问题：

| 维度     | 关键问题                                              |
| -------- | ----------------------------------------------------- |
| 目录结构 | page / component / hook / service / type 习惯放在哪？ |
| 命名规则 | 组件 PascalCase、hook 用 use 前缀、常量 UPPER_SNAKE？ |
| 状态管理 | 什么时候用 useState、抽 hook、上 Zustand/Context？    |
| 接口层   | 请求封装在哪、错误怎么处理、loading 怎么管？          |
| 提交规范 | commit message 格式、分支命名、PR 模板？              |
| 样式方案 | Tailwind class 顺序、何时抽组件、CSS Modules？        |

> **判断标准：** 如果你在两个项目里做了同一个决策两次，它就值得沉淀成规则。

## 四、第二层：沉淀规范（核心层）

Agent 不会"记住"你的习惯，它只会读取上下文里存在的规则。所以你要把习惯写成**显式、可执行、带判断条件**的规则文件。

### 规则文件 CLAUDE.md

在项目根目录创建 `CLAUDE.md`（或 `.cursorrules` / `AGENTS.md`），这是 Agent 每次对话都会自动读取的上下文文件。

```markdown
# 项目约定

## 目录结构

- src/pages/ 页面级组件，一个路由对应一个文件夹
- src/components/ 可复用组件，跨页面使用
- src/hooks/ 自定义 hook，以 use 开头
- src/services/ 接口请求层，每个领域一个文件
- src/types/ 全局类型定义

## 命名规则

- 组件：PascalCase（UserProfile.tsx）
- Hook：use 前缀（useAuth.ts）
- 常量：UPPER_SNAKE_CASE
- 接口类型：统一用 type 而非 interface（选一个坚持）

## 创建新页面时必须包含

1. index.tsx 页面主组件
2. styles.ts 页面专用样式
3. types.ts 页面相关类型
4. hooks/useXxx.ts 页面逻辑 hook
5. services/xxx.ts 接口请求

## 禁止事项

- 禁止在组件里直接写 fetch/axios
- 禁止 any，需要时用 unknown + 类型守卫
- 禁止 inline style 写动态样式
```

### 写规则的三个关键原则

1. **带触发条件：** "创建新页面时 → 必须生成这 5 个文件"，而不是泛泛说"保持目录清晰"
2. **可执行：** 能写成 checklist 让 Agent 照着做，而不是"注意代码质量"这种废话
3. **带反例：** 明确说"不要这样做"，比只说"要那样做"更有效

## 五、第三层：工程载体

光有规则文件还不够——Agent 可能会忽略，人也可能违反。要把规则变成**工具能强制执行的东西**。

| 载体                | 解决的问题     | 工具示例                      |
| ------------------- | -------------- | ----------------------------- |
| 脚手架模板          | 创建工程不完整 | plop / hygen 模板             |
| ESLint 自定义规则   | 代码规则有问题 | 禁止 any、强制 import 顺序    |
| TypeScript 严格配置 | 类型不严谨     | `strict: true`                |
| 组件库 / 代码片段   | 重复写样板     | 内部 PageTemplate、useRequest |
| commitlint + husky  | 提交不规范     | 提交前自动校验                |

### 脚手架示例（plop）

```javascript
// plopfile.js
module.exports = (plop) => {
  plop.setGenerator('page', {
    description: '生成标准页面结构',
    prompts: [{ type: 'input', name: 'name', message: '页面名称' }],
    actions: [
      {
        type: 'add',
        path: 'src/pages/{{name}}/index.tsx',
        templateFile: 'templates/page/index.hbs',
      },
      {
        type: 'add',
        path: 'src/pages/{{name}}/types.ts',
        templateFile: 'templates/page/types.hbs',
      },
      {
        type: 'add',
        path: 'src/pages/{{name}}/hooks/use{{name}}.ts',
        templateFile: 'templates/page/hook.hbs',
      },
      {
        type: 'add',
        path: 'src/services/{{name}}.ts',
        templateFile: 'templates/page/service.hbs',
      },
    ],
  })
}
```

这样无论是你还是 Agent，执行 `npx plop page` 都能生成完整、一致的页面结构。

## 六、第四层：自动校验与引用

最后一步是建立**反馈闭环**，让规则不只是"写在那里"，而是能被主动检查。

### 方法一：在 CLAUDE.md 里写自检指令

```markdown
## 生成代码后的自检清单

完成代码生成后，必须逐条检查：

- [ ] 是否有 any？如有，改为 unknown + 类型守卫
- [ ] 新文件是否在正确目录？
- [ ] 接口请求是否走 services 层？
- [ ] 组件是否超过 200 行？如是，拆分
      如有违反，先修正再输出。
```

### 方法二：Git Hooks 硬性拦截

```bash
# .husky/pre-commit
npx lint-staged    # 只检查暂存区文件
npx tsc --noEmit   # 类型检查
```

即使 Agent 生成了不合规代码，提交时也会被拦下来。

### 方法三：规则文档作为 Agent 的可引用资源

```markdown
## 详细规范

- 目录结构规范见 @docs/conventions/structure.md
- 命名规范见 @docs/conventions/naming.md
- 接口层规范见 @docs/conventions/api.md
  创建新模块前，先阅读对应规范文档。
```

## 七、落地建议：从最小闭环开始

不要一次性搞全套。建议按以下顺序推进：

| 阶段   | 行动                                 | 目标                                           |
| ------ | ------------------------------------ | ---------------------------------------------- |
| 本周   | 写第一版 CLAUDE.md                   | 目录结构 + 命名规则 + 禁止事项（最痛的三件事） |
| 下周   | 加 ESLint 严格规则 + TypeScript 配置 | 让工具帮你卡住底线                             |
| 第三周 | 写 plop 脚手架模板                   | 解决"创建工程不完整"的问题                     |
| 持续   | 每次发现 Agent 犯错就补充规则        | 建立自我进化的闭环                             |

## 总结

将个人开发习惯工程化的本质，是完成一次思维转变：

- **从依赖记忆到依赖文件：** 把习惯写入 `CLAUDE.md`，Agent 每次都能读到
- **从口头约束到工具约束：** 用 ESLint、TypeScript、Git Hooks 让违规代码无法通过
- **从人工纠偏到自动闭环：** 在规则中嵌入自检清单，让 Agent 自己检查自己

> 核心转变：**口述叮嘱 → 文件化规则 → 工具化校验**。规则文件让 Agent 知道怎么做，工程载体让它不得不这么做。
