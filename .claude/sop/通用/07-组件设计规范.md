# 组件设计规范

> 目标：解决"什么时候该抽组件""组件拆到多细"的决策问题。
> 核心原则：**先有职责边界，再有代码。**

---

## 1. 组件分层

| 层级         | 特征                             | 例子                                     |
| ------------ | -------------------------------- | ---------------------------------------- |
| **通用组件** | 跨模块可复用，与具体业务解耦     | `BasicTable`、`ConfirmModal`、`Uploader` |
| **业务组件** | 只在该领域内复用，与业务逻辑相关 | `UserFilterForm`、`OrderStatusBadge`     |
| **页面组件** | 路由入口，负责数据流编排和布局   | `UserListPage`、`DashboardPage`          |

### 原则

- 通用组件**不持有业务状态**，通过 props + callbacks 通信
- 页面组件**不做 UI 细节**，只做数据分配 + 布局
- 业务组件是业务逻辑的主要载体

## 2. 什么情况该抽组件（决策树）

```
组件里塞了多个不相关职责（数据获取 + 表单 + 列表 + 弹窗…）？
├── 是 → 评估拆分
│       ├─ 逻辑/数据相关 → 提取 hook / composable
│       └─ UI 块可独立 → 提取子组件
│
否 → 同一套稳定结构被 ≥ 2 份真实可变数据复用？
├── 是 → 抽成组件（两个真实、不同的适配器跨过 seam 才值得抽）
│
否 → 只有 1 份实例、纯粹想象未来复用？
├── 是 → 不抽（一份实例 = 假设的 seam，为想象中复用抽组件是浪费）
│
否 → 这个块有独立的加载/空态/错误态？
├── 是 → 抽成组件（让父组件不用管它的内部状态）
│
否 → 这个块影响父组件的布局灵活度？
├── 是 → 抽成组件（通过 slot/children 让父组件注入内容）
│
否 → 放当前文件，不抽
```

### 反例

```
❌ 一个组件 400 行，里面三段逻辑互不相关
✅ 拆成 3 个功能单一的组件，父组件只做编排

❌ 自定义了一个"带图标的按钮"，只用到一次，也没有复用迹象
✅ 直接用 UI 库的原生 `<Button>`，不包装
```

### 拆分的本质：稳定结构 × 可变数据

抽组件不是"看到代码重复就拆"，而是识别 **结构稳定、数据变化** 的重复片段：

- **稳定结构**（骨架：布局、层级、渲染方式）→ 固化为可复用组件
- **可变数据**（内容、数量、来源）→ 通过 props / slot 注入

判断信号：同一套骨架被多份数据实例复用（如多个商品区块、多个列表页）。骨架才值得提炼为**结构层**；否则只是复制粘贴。

常见落地形态之一（不是唯一）：区块结构 → `Section`（容器）+ `Heading` / `List` / `Card`（展示），数据从父级 props 逐层下发。拆几层由骨架复杂度决定，不套固定件数。

### 何时抽 hook / composable

hook 抽离对象是**逻辑**（状态 + 生命周期），不是 UI。满足任一即抽：

- 逻辑依赖 `ref` / `reactive` / 生命周期 / `watch` 等 Vue 特性（**有状态**）
- 同类逻辑跨组件复用 ≥ 2 处（不必等组件膨胀）
- 逻辑与 UI 解耦，可独立测试

反向约束：

- **无状态纯函数**（无响应式、无生命周期）→ 放 `src/utils/`，命名 camelCase，不叫 hook
- 一次性逻辑 / 纯展示 → 留在当前文件，不抽

> 命名：hook 用 `use` 前缀 + PascalCase（见 02-命名规则）；hook 可依赖 `utils/`，反向禁止。

### 深模块：小接口 × 深实现

组件、hook、api 模块都是模块。**接口 = 调用方必须知道的一切**（Props 类型 + Emits + `defineExpose` 方法 + 不变量/约束），不只是类型签名。设计时用以下判据：

- **深模块** = 小接口 × 深实现——调用方学一点点接口，就能驱动大量行为。浅模块 = 大接口 × 薄实现（只是透传）。
- **删除测试**：假设删掉这个组件 / hook，复杂度是消失了，还是散回 N 个调用方？消失 → 它只是透传，该删；散回 → 它在挣它的位置（如 `useChart`：小接口吞掉 init/watch/resize/dispose 全套生命周期，删掉它每个图表都要重写一遍）。
- **接口即测试面**：调用方和测试跨同一个 seam。测不到接口背后 → 模块形状不对。
- **依赖从接口传入，结果经回调回传**：组件不自己创建依赖（不内部 new / fetch），不直接改父状态——props 进、emits 出，测试自然跨同一 seam。
- **别为想象中复用抽 seam**：只有一个真实调用实例时 seam 是假设的；出现第二个真实、不同的调用才值得抽（见 §2 决策树）。
- **暴露面最小化**：`defineExpose` 是接口的一部分，只暴露必要方法，不把内部实例 / 状态整个交出去。
- **判据是职责与复用，不是行数**：组件多大不是拆的依据，看职责边界与真实复用（见 §2 决策树）。

## 3. 组件分类（容器 vs 展示）

|      | 容器组件                                              | 展示组件                                     |
| ---- | ----------------------------------------------------- | -------------------------------------------- |
| 职责 | 获取数据、管理状态、编排子组件                        | 渲染 UI、接收 props、触发回调                |
| 特征 | 调用数据请求、持有 state                              | 纯渲染逻辑、可独立测试                       |
| 示例 | `UserListPage`（调用 fetchUserListApi、传参给子组件） | `BasicTable`（只管渲染表格，不关心数据来源） |

### 约定

- 通用组件尽量写成展示组件（或少量的可控状态）
- 如果组件内部发了请求，它的复用性就降了一级 → 业务组件而非通用组件
- 容器/展示的分工先落结构层（见 §2），再谈具体角色

## 4. Props 设计原则

| 原则                            | 说明                                                      |
| ------------------------------- | --------------------------------------------------------- |
| **少而精**                      | Props 控制在 5-7 个以内；明显超出时评估拆分或改用 slot    |
| **传递明确数据**                | 传组件真正需要的数据；避免无边界透传 Store 或巨型可变对象 |
| **默认值必要**                  | 所有非必需 props 都给默认值                               |
| **类型精确**                    | `role: 'admin' \| 'user'` 比 `role: string` 好            |
| **不要用 boolean 开关切换模式** | 同一个组件不要既当表格又当卡片——拆成两个组件              |

### 反例对照

```
❌ props 传了整个 store 对象
✅ 只传组件真正需要的数据

❌ 把 400 行组件机械拆成多个文件
✅ 按职责边界和独立复用性决定是否拆分

❌ <UserCard mode="editable" />
✅ <UserCardEditor />

❌ <Modal :visible="show" title="批量删除" />
✅ <BatchDeleteModal :visible="show" />
```

## 5. 回调/事件设计原则

| 原则                        | 说明                                                                     |
| --------------------------- | ------------------------------------------------------------------------ |
| **以动作命名，而非 setter** | `update` / `delete` 而非 `setName` / `changeVisible`                     |
| **粒度适中**                | 不要传整个表单的 change，拆成按字段的回调                                |
| **回调参数类型明确**        | `select: (id: number) => void` 而非 `select: (payload: any) => void`     |

> emit 名不带 `on` 前缀（Vue 官方惯例；AntD 内置组件事件如 `@ok` / `@cancel` 除外）。
