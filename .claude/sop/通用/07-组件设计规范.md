# 组件设计规范

> 目标：解决"什么时候该抽组件""组件拆到多细"的决策问题。
> 核心原则：**先有职责边界，再有代码。**

---

## 1. 组件分层

| 层级         | 特征                             | 例子                                     |
| ------------ | -------------------------------- | ---------------------------------------- |
| **通用组件** | 跨模块可复用，与具体业务解耦     | `BasicTable`、`ConfirmModal`、`Uploader` |
| **业务组件** | 只在该领域内复用，与业务逻辑相关 | `UserFilterForm`、`OrderStatusBadge`     |
| **页面组件** | 路由入口，负责数据流编排和布局   | `UserListPage`、`DashboardPage`          |

### 原则

- 通用组件**不持有业务状态**，通过 props + callbacks 通信
- 页面组件**不做 UI 细节**，只做数据分配 + 布局
- 业务组件是业务逻辑的主要载体

---

## 2. 什么情况该抽组件（决策树）

```
组件文件超过 200 行？
├── 是 → 必须拆分
│       ├─ 逻辑/数据相关 → 提取 hook / composable
│       └─ UI 块可独立 → 提取子组件
│
否 → 同类 UI 结构出现 ≥ 2 次？
├── 是 → 抽成组件（即使现在不复用，未来大概率复用）
│
否 → 这个块有独立的加载/空态/错误态？
├── 是 → 抽成组件（让父组件不用管它的内部状态）
│
否 → 这个块影响父组件的布局灵活度？
├── 是 → 抽成组件（通过 slot/children 让父组件注入内容）
│
否 → 放当前文件，不抽
```

### 反例

```
❌ 一个组件 400 行，里面三段逻辑互不相关
✅ 拆成 3 个功能单一的组件，父组件只做编排

❌ 自定义了一个"带图标的按钮"，只用到一次，也没有复用迹象
✅ 直接用 UI 库的原生 `<Button>`，不包装
```

### 拆分的本质：稳定结构 × 可变数据

抽组件不是"看到代码重复就拆"，而是识别 **结构稳定、数据变化** 的重复片段：

- **稳定结构**（骨架：布局、层级、渲染方式）→ 固化为可复用组件
- **可变数据**（内容、数量、来源）→ 通过 props / slot 注入

判断信号：同一套骨架被多份数据实例复用（如多个商品区块、多个列表页）。骨架才值得提炼为**结构层**；否则只是复制粘贴。

常见落地形态之一（不是唯一）：区块结构 → `Section`（容器）+ `Heading` / `List` / `Card`（展示），数据从父级 props 逐层下发。拆几层由骨架复杂度决定，不套固定件数。

## 3. 组件分类（容器 vs 展示）

|      | 容器组件                                              | 展示组件                                     |
| ---- | ----------------------------------------------------- | -------------------------------------------- |
| 职责 | 获取数据、管理状态、编排子组件                        | 渲染 UI、接收 props、触发回调                |
| 特征 | 调用数据请求、持有 state                              | 纯渲染逻辑、可独立测试                       |
| 示例 | `UserListPage`（调用 fetchUserListApi、传参给子组件） | `BasicTable`（只管渲染表格，不关心数据来源） |

### 约定

- 通用组件尽量写成展示组件（或少量的可控状态）
- 如果组件内部发了请求，它的复用性就降了一级 → 业务组件而非通用组件
- 容器/展示的分工先落结构层（见 §2），再谈具体角色

## 4. Props 设计原则

| 原则                            | 说明                                                               |
| ------------------------------- | ------------------------------------------------------------------ |
| **少而精**                      | Props 控制在 5-7 个以内，超过考虑拆组件                            |
| **不要透传整个对象**            | 传 `user.name` + `user.email` 而非整个 `user` 对象（便于追踪变更） |
| **默认值必要**                  | 所有非必需 props 都给默认值                                        |
| **类型精确**                    | `role: 'admin' \| 'user'` 比 `role: string` 好                     |
| **不要用 boolean 开关切换模式** | 同一个组件不要既当表格又当卡片——拆成两个组件                       |

### 反例对照

```
❌ props 传了整个 store 对象
✅ 只传组件真正需要的字段

❌ <UserCard mode="editable" />
✅ <UserCardEditor />

❌ <Modal :visible="show" title="批量删除" />
✅ <BatchDeleteModal :visible="show" />
```

## 5. 回调/事件设计原则

| 原则                        | 说明                                                                     |
| --------------------------- | ------------------------------------------------------------------------ |
| **以动作命名，而非 setter** | `onUpdate` / `onDelete` 而非 `onSetName` / `onChangeVisible`             |
| **粒度适中**                | 不要传整个表单的 onChange，拆成按字段的回调                              |
| **回调参数类型明确**        | `onSelect: (id: number) => void` 而非 `onSelect: (payload: any) => void` |
